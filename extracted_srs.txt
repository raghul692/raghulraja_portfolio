1. Executive Summary
Portfolio AI is proposed as a dedicated AI subsystem around the personal portfolio rather than a basic chat widget. It will ingest and normalize portfolio pages, project descriptions, technology stacks, repository documentation, resume content and selected career-preparation knowledge. A retrieval layer will then supply evidence to an LLM so answers remain tied to the portfolio owner’s actual data. The design follows established RAG patterns: hybrid retrieval is valuable when both exact technical keywords and semantic similarity matter, which is especially relevant for recruiter queries and ATS analysis. NVIDIA’s RAG guidance explicitly describes combining sparse keyword retrieval such as BM25 with dense vector retrieval, and Google’s reference architectures describe RAG systems with managed vector search and PostgreSQL-compatible vector storage patterns.
The product has four major AI modes: Portfolio Q&A; ATS Resume Checker; ATS Resume Builder; Placement Preparation Coach. A fifth cross-cutting capability, Knowledge Sync, keeps the AI knowledge base aligned with portfolio changes. GitHub repository webhooks can trigger ingestion when the source repository changes, while scheduled reconciliation provides a safety net.
2. Product Vision
Create one personal AI system that can answer: “Who is this candidate?”, “What did he build?”, “Why did he choose this technology?”, “How does this project work?”, “Is this resume ATS-friendly for this role?”, “What keywords are missing?”, and “How should he prepare for the placement process?” - while separating factual portfolio evidence from generated coaching content.
3. Goals
Answer portfolio questions using only verified portfolio knowledge whenever a factual claim is requested.
Retrieve exact project names, technologies, features, architecture, outcomes, repository links and resume evidence.
Analyze an uploaded resume against a job description with ATS-oriented structure and keyword checks.
Generate an editable ATS-friendly resume tailored to a target role using only verified candidate facts.
Provide aptitude, grammar, vocabulary, verbs, group discussion, technical and HR-round preparation.
Automatically detect portfolio/repository changes and update the AI knowledge base without manual re-training.
Expose source citations/evidence for factual answers and maintain knowledge-version lineage.
Provide an admin/owner dashboard to inspect sync status, documents, chunks, retrieval quality, evaluations and failed jobs.
4. Non-Goals
The model will not invent achievements, internships, certifications, percentages, employers, metrics or technologies.
The system will not claim a resume is guaranteed to pass every ATS; different ATS products have different parsing and ranking behaviors.
The system will not treat “IEEE standard” as a universal ATS resume specification. IEEE-style technical quality can be used as a documentation and writing-quality benchmark, while ATS compatibility remains a separate concern.
The public assistant will not expose private documents or owner-only analytics.
Fine-tuning is not required for v1; retrieval plus strong prompting, schemas and evaluation is the preferred first architecture.

11. Retrieval Strategy
Classify the user query into one or more intents: portfolio_factual, recruiter_fit, ATS, resume_build, placement_practice, interview, general.
Extract exact entities and keywords such as project name, technology name, job title and skill aliases.
Run dense vector retrieval for semantic similarity.
Run sparse/full-text retrieval for exact keywords, technologies and names.
Fuse results using weighted hybrid ranking; technical/ATS queries should bias toward sparse matching when exact terms are important.
Apply metadata filters such as visibility, document type and current knowledge version.
Rerank the top candidates and build a compact evidence context.
Generate a response with citations/metadata and a “not found” behavior when the evidence is insufficient.
12. LLM Orchestration
Use the LLM as a controlled reasoning/generation layer, not as the database. Every important workflow gets an explicit system prompt, retrieval contract, JSON schema and validator. Structured outputs are preferable for ATS reports, extracted job descriptions, resume sections and scoring records because the model response can be constrained to a defined schema.
13. Portfolio Sync / Near-Real-Time Update Design
Enable a repository webhook for push events on the portfolio repository and relevant project repositories. GitHub supports repository webhooks and push-event payloads.
Webhook endpoint validates a secret/signature and immediately returns 2xx after placing an idempotent job on the queue.
Worker resolves the commit SHA, fetches changed files, pages or documentation, and ignores irrelevant files such as build output or node_modules.
Normalizer converts source content to clean canonical text plus typed entities.
Document versioning compares content hashes. Unchanged content is skipped.
Only changed chunks are embedded and indexed; deleted chunks are marked inactive.
Knowledge snapshot version is advanced after successful indexing.
Cache invalidation ensures new conversations use the newest successful snapshot.
A scheduled nightly reconciliation checks that webhook processing did not miss a change.
14. ATS Resume Checker Design
The checker must be more than a keyword counter. It should model at least six dimensions: parseability, structure, job-description alignment, skills coverage, evidence/impact quality and consistency. Harvard recommends basic formatting, explicit skills and contextual keywords; Berkeley advises standard formatting, common section titles and avoiding layout elements that can confuse ATS parsing.

15. ATS Scoring Model - Proposed
Initial scoring formula (tunable after evaluation): Total = 20% parseability + 15% structure + 25% keyword/JD alignment + 15% skills coverage + 15% evidence quality + 10% consistency. The product must show sub-scores and evidence rather than a single unexplained number. A job-specific score is not a guarantee of recruiter selection.
16. ATS Resume Builder Design
User selects target role and optionally pastes a job description.
AI extracts required/preferred skills and responsibilities.
Portfolio knowledge is queried for verified evidence.
Candidate facts are transformed into role-specific bullets using action-context-result structure where appropriate.
Unsupported claims are rejected by a fact validator.
Resume sections are assembled into an ATS-safe template using conventional headings.
User previews/edit the result, then downloads DOCX/PDF.
Generated resume receives a post-generation ATS parse simulation and a final checker report.

20. Security Architecture
LLM and GitHub credentials are server-side only.
GitHub webhook requests are authenticated and replay-protected.
Portfolio public content and private owner content are separated at the retrieval-filter level.
Resumes are encrypted at rest where supported and access-controlled by user ownership.
File uploads are validated by MIME type, extension, file size and malware scanning where available.
Rate-limit public chat and protect expensive AI endpoints from abuse.
Never include secrets, private tokens or environment variables in the RAG corpus.
Keep prompt-injection defenses in both retrieval and generation: retrieved text is data, not instruction authority.
21. Prompt / Guardrail Contract
System prompt policy for factual portfolio mode: “Use retrieved evidence as the only authority for candidate-specific facts. Do not invent. When evidence is missing, state that it is not found. Distinguish verified facts, user-provided facts and general advice. Cite the evidence used.” For ATS mode: “Analyze the uploaded resume and job description first. Do not add skills unless supported by the resume or verified portfolio.” For resume generation: “Generate only from the verified candidate fact set.”
22. Evaluation Strategy
Create a fixed evaluation set before production. It should contain at least: 50 portfolio factual questions, 20 recruiter-fit questions, 20 ATS/JD pairs, 20 resume-bullet transformations, 20 HR questions and 20 technical interview questions. Human-labeled answers become the regression benchmark. Each deployment must report grounded accuracy, unsupported-claim rate, retrieval hit rate, citation coverage and schema validity.

27. Cost-Control Strategy
Use retrieval before generation so only small, relevant context reaches the LLM.
Cache stable portfolio answers and embeddings.
Use a smaller model for classification, extraction and scoring where quality remains acceptable.
Use a stronger model only for complex resume rewriting or interview reasoning.
Batch embedding updates and only re-embed changed chunks.
Keep a hard token budget per request and rate-limit anonymous users.

30. MVP Recommendation
Do not build all modules at once. The best MVP is: (1) portfolio ingestion, (2) hybrid RAG, (3) grounded Portfolio Q&A, (4) JD analysis + ATS checker, and (5) GitHub-based auto-sync. Once these are reliable, add Resume Builder and Placement Coach. This ordering reduces the risk of building a beautiful frontend on top of an unreliable knowledge system.
31. Definition of Done for Portfolio AI v1
Portfolio AI can answer at least 50 curated candidate questions with >= 90% factual accuracy.
Every candidate-specific answer exposes evidence metadata.
A GitHub push results in a new knowledge snapshot without manual re-upload.
ATS checker can compare a resume with a job description and show actionable gaps.
Resume Builder uses only verified candidate facts and produces parser-friendly DOCX/PDF.
Owner can run and review aptitude, grammar, GD, HR and technical practice sessions.
Private resume/owner data cannot be retrieved from public chat.
Tests, logging, monitoring and rollback procedures are documented and automated in CI/CD.
